# レガシープロジェクトを安全に AI 駆動開発できる状態にする

## このスキルの位置づけ

仕様や経緯が失われたプロジェクトを、次の順で改善する。

- 段階0: 現状診断と方針書の作成
- 段階1: 仕様の復元
- 段階2: 振る舞いの固定と、あるべき形への修正
- 段階3: ガードレールの整備
- 段階4: 完了条件の確認と運用
- 段階5: 繰り返す誤りを構造に落とす改善ループ

エージェントは作業を進めながら方針書を作り、段階が進むたびに更新する。

- 段階は厳密な直列ではない。規模が大きい場合は領域ごとに段階1〜2を回し、全体に行き渡ってから段階3に進む。
- 数値（問数の上限、カバレッジの目標、再発回数の閾値など）はこのスキルでは決めない。プロジェクトごとに仮置きして「要確認」と書き、実測後に見直す。
- ツールの仕様（lint ルールの挙動、型チェッカーの設定、AI エージェントのルールファイルやスキルの名前・置き場所・読み込まれ方、CI の機能、形式検証ツールの対応言語）は記憶で断定しない。実物や公式文書で確かめ、確かめていないものは「要確認」と書く。
- 文中の（S1）〜（S6）、（G1）（G2）、（K: スキル名）は、末尾の「出典」に対応する。出典のない記述は、このスキル自身の方針である。

## 安全性を何で担保するか

このスキルは、変更の安全性を「人が差分を読むこと」で担保しない。エージェントが変更を出す速さでは、人がすべての変更を丁寧に読むことはできない（S5）。同じ誤りを毎回レビューで拾う状態は、直すべき問題そのものである（G2）。

代わりに、次の5つで担保する。

1. **繰り返す誤りを、構造で起こせなくする**: 強制力の高い順に選ぶ（S2、S5、G2、K: correct）。
   1. 設計やデータ構造で、誤りそのものをなくす。
   2. 型で書けなくする。書けてしまうなら、lint や CI の検査で止める。エラーメッセージには、代わりに使うべきものを書く。
   3. テストで捕まえる。
   4. 文書やエージェント向けのルールに書く。守られなくても何も失敗しないので、最後の手段にする。

   人のレビューは、この序列に入れない（G2）。
2. **ユーザーと同じ操作で動かして確かめる**: アプリを起動し、利用者と同じ経路で操作し、証拠を残す手順を、プロジェクト内の検証スキルとして持つ（G1、K: create-verification-skill）。
3. **危険度の高い箇所は形式検証する**: 破れたときの害が大きく、テストが届きにくい性質は、範囲を明示したうえで全ケースを検査する（G1、K: create-formal-verification-skill）。
4. **検証できる小さな単位で積む**: 各単位は検査で終わる。通るまで次に進まない（K: principle-sequence-verifiable-units）。
5. **成果物で証明する**: 「コンパイルが通った」は証拠にしない（G1）。実物を動かした結果（実行したコマンドと出力、失敗してから通ったテスト、画面の記録など）を示す（K: principle-prove-it-works）。

### この方針の限界と、移行の進め方

- 検査が確かめられるのは「決めたとおりに動くか」までである。「何が正しいか」は検査では決まらない。レガシープロジェクトでは、その答えがコードにないことが出発点なので、仕様の判定と方針の承認は人に残す（後述の「人の判断が残る箇所と理由」）。
- 段階0〜2では、構造による保証がまだ薄い。この間は人の確認が多く残る。保証の手段が整い、実際に誤りを止めることを確かめた種類の変更から、人のレビューを外す。確かめる前に外さない。
- 人のレビューで指摘が出たら、それを「保証が欠けている箇所」として記録し、段階5で構造に落とす。同じ指摘を人が2度しなくて済む状態を目指す。
- コードを動かさずに読むだけのレビューを、エージェントに何度も重ねさせない。価値が低く、細かい指摘に流れやすい（S6）。エージェントに確認させるなら、実行した結果か、決定的な検査の結果を出させる。

### 段階ごとの保証の一覧

| 段階 | 人のレビューの代わりに保証するもの | 人の判断が残る箇所 |
|---|---|---|
| 0 | 実行したコマンドと出力の記録、何もない状態からの再現 | 方針と優先順位の承認 |
| 1 | 根拠へのポインタ、仮説と確定の状態の機械的な区別 | 仮説の確定、あるべき仕様の決定 |
| 2 | 特性テスト、失敗するテストを先に置く順序、前後で変わらないテスト結果、判定の台帳 | 仕様どおりかバグかの判定、挙動を変える変更の取り込み |
| 3 | 設計・型・lint・テストによる強制、検証スキル、形式検証、「検査が実際に落ちること」の証明 | 何を守るかの決定、例外と緩和の承認 |
| 4 | 完了条件つきの依頼、検証スキルによる証拠、書き手とは別のエージェントによる実行検証 | 任せる範囲の拡大、リリースの承認 |
| 5 | 誤りの種類ごとの構造的な対策、過去の誤りでの検査の証明、ルールと強制手段の対応表 | 緩める変更の承認、ループ自体の設定 |

## 着手前の確認

次が確認できるまで、コードや資料を外部の AI サービスに送らず、変更もしない。

1. **契約と機密**: 外部の AI サービスにコードや資料を送ってよいかを、依頼者に確認する。了承がなければ、許可された範囲（たとえば端末内の処理だけ）に縮小する。
2. **書き込みの範囲**: エージェントがどのブランチ・環境まで触ってよいかを確認する。本番環境と本番データには、明示の許可なく触らない。
3. **判断を担う人**: 仕様を決める人、挙動を変える変更の取り込みを判断する人、リリースを承認する人、ガードレールの変更を承認する人を役割名で確認する。いない役割は方針書のリスクに書く。

## 段階をまたぐ原則

1. **検証できる小さな単位で積む**: 1つの変更は、単独で検証でき、単独で取り消せる大きさにする。各単位は「確かな状態 → 変更を1つ → 検査を実行 → 次へ」の形にし、検査が通るまで次に進まない（K: principle-sequence-verifiable-units）。検証の方法を説明できない変更は、さらに分ける。
2. **証明になる順に積む**: 失敗するテストを先に、修正を後にする。削除を先に、作り替えを後にする。基準の測定を先に、変更を後にする（K: principle-sequence-verifiable-units）。
3. **挙動を変える変更とリファクタリングを分ける**: 同じコミットや同じ検証の単位に混ぜない。リファクタリングは「テストの結果が前後で変わらない」ことを確認する。挙動を変える変更は「どのテストの期待値が、なぜ変わったか」を説明する。
4. **成果物で証明する**: 完了の報告には、実物を確かめた結果を付ける。実行したコマンドと出力、読み戻した値、画面や端末の記録などである。代理の指標（コンパイルが通った、自己申告、キャッシュされた出力）は証拠にしない（G1、K: principle-prove-it-works）。
   - 検査は、できるだけスクリプトにして繰り返せるようにする。
   - 検査が失敗したら、対象より先に観察の方法を疑う（K: principle-prove-it-works）。
   - 確かめられなかったものは「未確認」と書く。根拠のない自信のある報告は、警告として扱う（G1）。
5. **書いた者が判定しない**: 変更を書いたエージェントとは別のエージェントが、実物を動かして検証する（G1）。動かさずに読むだけの確認は、検証に数えない（S6）。
6. **段階的に置き換える**: 一括の書き直しはしない。次の手法から、対象に合うものを選ぶ。
   - ストラングラーパターン: 新しい実装を旧実装の外側に置き、呼び出しを少しずつ移す。
   - 抽象化によるブランチ: 境界にインターフェースを入れ、内側を差し替える。
   - 切り替えフラグ: 新旧を切り替えられるようにする。
   - 並行稼働: 新旧の結果を比較する。

   どの手法でも、旧経路を消す条件を先に決める。古いやり方が残ると、エージェントは近くにある例をまねるので、移行が済んだら消す（K: correct）。
7. **リスクの高い箇所から**: 優先度は「壊れたときの影響（金銭、データ、権限、外部連携）」「変更の頻度」「理解できていない度合い」で決める。きれいにしやすい箇所から始めない。
8. **仮説と確定を分ける**: AI が読み取った内容は、決定者が確認するまで仮説として扱い、記録の上でも区別する。
9. **正本は1か所**: 仕様・用語・決定の正本は、バージョン管理された1か所に置く。チャットや通話は入力口であり、正本に書き戻した時点で確定とする。
10. **分からないことは記録して止まる**: 推測で埋めない。未決事項として残し、質問票に回す。
11. **戻せる状態を保つ**: 変更の前に、戻す手順（リバート、フラグの切り戻し、データの復元）を確認する。戻せない操作は人の承認を取る。
12. **決定の記録を残す**: 長い作業や無人の作業では、決定ごとに1行の記録を残す。項目は、時刻、段階、決めたこと、理由、証拠へのポインタ（コミット、ファイルの場所、成果物のパス）、結果である。追記だけを行い、誤った行は消さずに新しい行で上書きする（K: show-me-your-work）。人は全体を読み直さず、この記録の証拠をたどって抜き取りで確かめる。

## AI に任せてよい作業と、人の判断が必須の作業

| 区分 | 作業 |
|---|---|
| AI に任せてよい（結果は検査と成果物で保証する） | コード・履歴・チケットの調査と要約、仮説の作成、質問票の下書き、用語集や ADR の下書き、特性テストの下書き、テストで守られた範囲の機械的なリファクタリング、lint や型のエラーの修正、検証スキルによる動作の確認、失敗事例の収集と分類、構造的な対策の案の作成と、その証明 |
| 人の判断が必須 | 仮説を確定に変えること、「仕様どおりかバグか」の判定、あるべき仕様（To-Be）の決定、方針書の承認、挙動を変える変更の取り込み、テストの削除・スキップ・期待値の変更、ガードレールを緩める変更と例外の承認、データ移行やスキーマ変更、認証・権限・金銭・個人情報に関わる変更、外部連携の変更、依存関係の大きな更新、本番へのリリース、エージェントの権限の変更 |
| AI がしてはいけない | 確認なしに仮説を確定として書く、テストを通すために期待値やチェックを書き換える、検査を通すために検証する性質やモデルを弱める、承認の範囲を自分で広げる、自分の変更を自分で合格と判定する、了承のない外部サービスへコードや録音を送る |

「AI に任せてよい」作業でも、保証の手段がまだない種類の変更は、手段が整うまで人が確認する。

迷ったときは、次の3つに1つでも当てはまれば人の判断に回す。

- 取り消せない
- 外部に影響する
- 「何が正しいか」を決めている

### 人の判断が残る箇所と理由

人に残すのは、差分を読んで誤りを探す作業ではなく、次の判断である。人には、差分の全行ではなく、判断の材料と証拠を短く示す。

| 残す判断 | 残す理由 |
|---|---|
| 仮説の確定、仕様どおりかバグかの判定、To-Be の決定 | 検査は「決めたとおりか」を確かめる。「何を正とするか」は、コードにも検査にも書かれていない。失われた文脈は、決定者に聞くしかない |
| 方針書と優先順位の承認 | どのリスクを取り、どこに力を使うかは、事業と契約の判断である |
| 挙動を変える変更の取り込み | 期待値の変更が判定の記録と結びついているかは機械で確かめられる。しかし、利用者や既存データへの影響を受け入れるかは判断である |
| テストや検査を緩める変更、例外の承認 | 緩める変更は、保証そのものを減らす。検査では自分自身の緩和を止められない。例外には、理由、期限、人の承認を付ける（K: correct） |
| 取り消せない操作（本番へのリリース、データの削除や移行、外部への送信） | 誤ったときに戻せない。検査がすべて通っていても、取り込みやリリースは別の判断である（G1） |
| エージェントの権限と、任せる範囲の変更 | 保証の前提を変える判断だからである |

## 段階0: 現状診断

### 目的

どの段階にどれだけ力を使うかを決め、方針書の初版を作る。

### 入力

- リポジトリ、ビルドとデプロイの設定
- チケットやドキュメント（あれば）
- 依頼者からの聞き取り

### 手順

1. 次の観点を調べる。実際にコマンドを動かして確かめたものと、読んだだけのものを分けて記録する。動かしたものは、コマンドと出力を残す。

   | 観点 | 見ること |
   |---|---|
   | 規模と構造 | 言語、行数やモジュール数のおおよそ、依存関係、変更が集中している箇所、長く触られていない箇所 |
   | テスト | 有無、種類、実際に通るか、実行時間、どの領域を守っているか |
   | 型 | 静的型の有無、型チェックの厳しさ、型を迂回している箇所 |
   | ビルド・デプロイ | 手順が文書化されているか、手元で再現できるか、CI の有無、デプロイが手作業か自動か、戻す手順があるか |
   | 動かして確かめる手段 | アプリを手元で起動できるか、利用者と同じ操作をスクリプトで行う仕組み（既存の E2E テストや操作用のスクリプトなど）があるか、複数を並べて起動できるか |
   | ドメイン知識 | 仕様を決められる人、経緯を知る人がいるか。連絡が取れるか、いつまで取れるか |
   | 運用の状況 | 本番で稼働中か、障害や不具合の報告、監視とログ、変更を止めるべき時期 |
   | 繰り返されている誤り | 取り消された変更、過去のレビューの指摘、回避策を説明するコメント、lint の無効化の増え方（段階5の最初の入力になる） |
   | 資料 | 設計書、チケット、過去の議論の記録がどこにどれだけあるか |

2. 診断の結果から優先順位を決める。

   | 診断の結果 | 優先すること |
   |---|---|
   | ビルドや実行が手元で再現できない | 他のどの段階よりも先に、再現できる手順を作る。壊れた土台の上で作った検証の手順は、誤った手順を教える（K: create-verification-skill） |
   | 知識を持つ人がいるが、近く離れる見込み | 段階1のヒアリングを最優先にする。コードの調査は、質問を作るのに必要な範囲に絞る |
   | 知識を持つ人がいない | コード・履歴・ログを根拠に仮説を作る。段階2の特性テストを厚くする。判定は現在の責任者に求め、根拠が弱いことを記録する |
   | テストがない、または通らない | 変更の予定がある箇所とリスクの高い箇所から特性テストを置く。全体のカバレッジは追わない |
   | テストはあるが型がない | 段階1〜2を進め、型は境界から段階的に入れる（段階3） |
   | 進行中の障害や緊急の修正がある | その箇所だけ特性テストを置いて最小の修正をする。残りは通常の順に戻す |
   | 規模が大きい | 領域に切り、リスクの高い1領域で段階1〜2を通して進め方を確かめてから広げる |
   | デプロイが手作業で、戻す手順がない | 挙動を変える変更の前に、戻す手順を作る |

3. 方針書（後述のテンプレート）の初版を作り、依頼者に承認を求める。

### 人のレビューの代わりに保証するもの

| 保証したいこと | 手段 | 証拠 |
|---|---|---|
| 診断が事実である | 「実行した／読んだ／聞いた」を分けて記録する | 実行したコマンドと出力 |
| ビルドと実行が再現できる | 何もない状態から、文書の手順だけで実行する。可能なら1つのコマンドにまとめる | その実行の記録 |

人の判断が残る箇所: 方針書と優先順位の承認。理由は「人の判断が残る箇所と理由」のとおり。

### 成果物

- 診断の記録（コマンドと出力を含む）
- 方針書の初版

### 完了条件

- 観点ごとに「確認済み／未確認」が書かれている。
- 優先順位と理由が書かれている。
- 判断を担う人が役割名で決まっている。

### 次の段階に進む判定

依頼者が方針書の優先順位に同意している。ビルドと実行が再現できない場合は、先にそれを解決する。

## 段階1: 仕様の復元

### 目的

コードに書かれていない文脈を取り戻し、用語と決定を正本に残す。以後の「仕様どおりかバグか」の判定の根拠を作る。

### 入力

- コード、コミット履歴、レビューの記録、チケット、既存の文書
- 許可された範囲の過去のやり取り
- 段階0の診断の記録

### 手順

1. **体制を確認する**: 機能領域ごとに、決める人（決定者）と詳しい人（相談先）を役割名で一覧にする。質問の宛先と、決定の記録の「誰が決めたか」はここから引く。
2. **聞く前に掘る**: コード、履歴、チケットを調べ、分かることは聞かない。
   - 分かったことは、仮説として用語集に仮置きする。
   - 根拠（コミット、レビュー、チケット、コードの場所）を必ず添える。根拠のない仮説は書かない。
   - 動かして確かめられる仮説（「この入力でこう動く」）は、聞かずに動かして確かめ、結果を根拠にする。
3. **論点を整理する**: 疑問を漏れと重複がないように分類する。
   - 分類の例: 用語／業務ルール／例外処理／権限／外部連携／非機能
   - 答えで実装や判定が変わらない質問は捨てる。
   - 各質問に「答えがないと止まるか」と優先度を付ける。
4. **現状と理想を分ける**: 「今こう動いている」（As-Is）と「本来こうあるべき」（To-Be）を別の質問にする。
   - As-Is は、コードから立てた仮説の確認だけを求める。
   - To-Be は決定者に聞く。
5. **仮説つきの選択式の質問票を作る**:
   - 冒頭に要旨（状況、困りごと、問い、こちらの案）、回答の期限、所要時間の見込み、宛先を書く。
   - 各問に、仮説、根拠、選択肢、「分からない（詳しい人は誰か）」の逃げ道、止まるかどうかを必ず入れる。
   - 自由記述の質問は少数に絞り、通話に回す。
   - 1票の問数と所要時間に上限を置く（値は要確認。初回の実測後に見直す）。止まる質問を優先する。

   質問の形の例:

   ```markdown
   ## Q1［止まる／優先度 高／分類: 業務ルール］
   - 仮説: （コードと履歴から読み取った内容）
   - 根拠: （コミット、レビュー、チケット、コードの場所、動かした結果）
   - 選択肢: [ ] はい　[ ] いいえ（違う点を一言）　[ ] 分からない（詳しい人: ＿＿）
   - 答えがないと止まる箇所: （作業の名前）

   ## Q2［止まらない／優先度 中／分類: 例外処理］
   - 現状（As-Is）: （今の動き）
   - 質問（To-Be）: 今後はどうあるべきですか
   - 選択肢: [ ] A: 現状のまま　[ ] B: （案）　[ ] C: その他（一言）
   - こちらの推奨: （案と理由）
   ```

6. **ためて、まとめて、非同期で聞く**: 質問は束ねて送る。頻度は回答者と決める（要確認）。通話をする場合は先に質問票を送り、選択式は事前に答えてもらう。通話は、答えが割れた点と背景の深掘りにだけ使う。
7. **背景を聞く**: 「なぜこの仕様か」は、決定の記録の背景欄が埋まるまで聞く。責める形にせず、経緯を聞く。通話を録音・文字起こしする場合は、毎回同意を取る。
8. **脱線を退避する**: 今決めなくてよい話題は保留リストに移し、再検討の時期を一言書く。
9. **書き戻す**: 回答を次の形で正本に反映する。変更として出し、回答者か決定者の確認をもって確定とする。
   - **用語集**: 1用語1ファイルを基本にする。項目は、用語、別名（コード上の識別子との対応を含む）、関連語、分類、状態（仮説／確定／廃止）、決めた人（役割名）、決めた日、根拠、関連するコードの場所、関連する決定の記録。
   - **ADR（決定の記録）**: 背景、決定、理由、検討した他の案、影響。
   - **コードコメント**: コードを読むときに必要な最小限だけを書き、詳細は用語集と ADR を参照させる。
   - 未決事項は、次回の質問票に回す。
10. **仮説が確定扱いで広まるのを防ぐ**: 状態が仮説のものは、文書の上でも表示の上でも区別する。エージェントは、仮説を根拠に挙動を変える変更をしない。

用語集、ADR、質問票の置き場所や表示の方法（リポジトリ内の文書、課題管理、静的サイトなど）は、プロジェクトの環境に合わせて選ぶ。条件は次の2つである。

- 正本が1か所である。
- 変更の履歴が残る。

### 人のレビューの代わりに保証するもの

| 保証したいこと | 手段 | 証拠 |
|---|---|---|
| 仮説に根拠がある | 根拠の欄を必須にする。根拠が指すコミットやファイルが実在するかを検査する（検査の方法は要確認） | 検査の結果 |
| 仮説と確定が混ざらない | 状態、決めた人、決めた日を必須の項目にし、欠けた文書を形式の検査で止める（方法は要確認） | 検査の結果 |
| 文書とコードがずれない | 用語集の識別子の対応や、確定した業務ルールのうち、機械で検査できるものは段階2〜3でテストや lint に移す | 対応するテストや検査へのリンク |

仕様の文書とコードのずれは、エージェントがおおむね同期を保つとしても、強制されていなければ起こる（S6 のスレッド内の返信）。文書だけに置いた仕様は、最も弱い保証であると考える。

人の判断が残る箇所: 仮説の確定と To-Be の決定。理由は「人の判断が残る箇所と理由」のとおり。ここでの人の役割は、文書の査読ではなく、選択式の質問への回答である。

### 成果物

- 体制の一覧
- 用語集
- ADR
- 質問票と回答の記録
- 保留リスト
- 未決事項の一覧

### 完了条件

対象の領域について、次を満たす。

- 止まる質問がすべて確定しているか、決定者が保留を明示している。
- 主要な用語が、確定の状態で用語集にある。
- 仮説のまま残っているものが一覧になっている。

### 次の段階に進む判定

- 対象の領域で、振る舞いの正否を判定できるだけの根拠（確定した用語と決定）がある。
- 全体の完了は待たない。領域ごとに段階2へ進み、段階2で出た疑問は段階1の質問票に戻す。

## 段階2: 振る舞いの固定と、あるべき形への修正

### 目的

現状の振る舞いをテストで固定したうえで、不具合を含めてあるべき形に直す。判定の結果を記録に残す。

### 入力

- 段階1の用語集と ADR、未決事項の一覧
- 対象のコード
- 不具合の報告、ログ（あれば）

### 手順

1. **対象を選ぶ**: リスクが高い箇所と、変更の予定がある箇所から始める。1回の対象は、単独で検証できる大きさにする。
2. **特性テストを置く**: 修正の前に、現状の振る舞いをそのまま固定するテストを書く。
   - 正しいかどうかは、この時点では問わない。現状が誤りに見えても、まず現状のとおりに固定する。
   - 入力と出力が観察できる境界（公開された関数、API、画面、出力ファイルなど）で書く。利用者から観察できるもの（戻り値、エラー、読み戻せる状態、外部への作用）を表明し、内部の呼び出し順や途中のデータには結びつけない（K: principle-test-behavior-not-implementation）。
   - テストできない構造の場合は、テストを差し込むための最小限の変更だけを先にする。その変更は単独で検証する。
   - 時刻、乱数、外部サービスなど、結果が揺れる要因は固定するか差し替える。
   - 「現状を固定しただけで、正しさは未判定」と分かる印を付ける。
3. **テストが守れているかを確かめる**: テストごとに、次の2つの編集を想定する（K: principle-test-behavior-not-implementation）。リスクの高い経路では、実際に試して確かめる。
   - 振る舞いを壊したら、テストが落ちるか。落ちなければ、そのテストは何も証明していない。
   - 観察できる結果を保ったまま内部だけを変えたら、テストが通り続けるか。落ちるなら、実装に結びつきすぎている。
4. **仕様どおりかバグかを判定する**: 固定した振る舞いを一つずつ、段階1の記録と照らす。判定するのは決定者であり、エージェントは判定の材料と推奨を出す。

   | 判定 | 扱い |
   |---|---|
   | 仕様どおり | テストを正式な仕様のテストに昇格し、根拠（用語、ADR）を結びつける |
   | バグ | 修正の対象にする。影響範囲と、既存のデータや利用者への影響を確認する |
   | 仕様ではないが依存されている | すぐに直さない。互換を保つ方法か移行の方法を決定者と決め、ADR に残す |
   | 不明 | 段階1の質問票に回す。それまで挙動は変えない |

5. **判定を記録する**: 判定の台帳に次を残す。
   - 対象の振る舞い、判定、根拠、決めた人（役割名）、決めた日、対応する変更とテスト
6. **修正する**: バグと判定されたものを直す。
   - 先に、あるべき振る舞いのテストを書き、失敗することを確かめる。次に修正し、通ることを確かめる。この2つを別のコミットとして順に積む（K: principle-sequence-verifiable-units）。
   - 特性テストの期待値を変える場合は、判定の記録を理由として示す。
   - 挙動を変える変更とリファクタリングは分ける。
   - 影響が大きい修正は、段階的に置き換える手法（原則6）と、戻す手順を用意する。
   - データの修正や移行が要る場合は、人の承認を取り、別の作業として切り出す。
   - 直したバグは、段階3と段階5で「検査が実際に落ちること」を確かめる事例として残す。
7. **構造を整える**: テストで守られた範囲で、読みにくさや重複を直す。テストの結果が前後で変わらないことを確認する。
8. **検証する**: テストとビルドに加えて、実物を動かして確かめる。結果は事実のまま報告する。通らなかったものや、確かめていないものは、そのとおりに書く。
9. **形式検証の候補を挙げる**: 作業の中で、破れたときの害が大きく、テストが届きにくい性質（並行する処理、リトライ、状態の遷移、順序の入れ替わりなど）を見つけたら、候補として記録する。実施は段階3で判断する。

### 人のレビューの代わりに保証するもの

| 保証したいこと | 手段 | 証拠 |
|---|---|---|
| リファクタリングが挙動を変えていない | 特性テストの結果が前後で同じ。変更を挙動の変更と分ける | 前後のテスト結果 |
| 修正が、狙った振る舞いを直している | 失敗するテスト、次に修正、の順で積む | 失敗の記録と、通った記録 |
| テストが実際に守っている | 振る舞いを壊すとテストが落ちることを試す | 試した結果 |
| 期待値の変更が勝手に行われていない | 期待値の変更を、判定の台帳の項目と結びつける。結びつきのない変更を検査で止める（方法は要確認） | 台帳の項目と変更の対応 |

人の判断が残る箇所: 仕様どおりかバグかの判定と、挙動を変える変更の取り込み。理由は「人の判断が残る箇所と理由」のとおり。決定者に示すのは、差分の全行ではなく、固定した振る舞い、判定の材料、期待値の変化、動かした証拠である。

### 成果物

- 特性テストと仕様のテスト
- 判定の台帳
- 修正とリファクタリングの変更
- 更新した用語集と ADR
- 直したバグの事例（検査の証明に使う）
- 形式検証の候補の一覧

### 完了条件

対象の領域について、次を満たす。

- リスクの高い経路が、テストで守られている。
- 固定した振る舞いのすべてに、判定が付いている（不明を含めて一覧になっている）。
- バグと判定されたものが、修正済みか、対応の時期が決まっている。
- 「未判定」の印が残っている箇所を把握している。

### 次の段階に進む判定

- 予定した領域の全体に段階1〜2が行き渡り、テストが安定して通る（結果が揺れるテストが残っていない）状態になったら、段階3に進む。
- テストを CI で自動実行するなどの最小限の仕組みは、段階2の途中で入れてよい。厳しい規約の一斉適用は段階3まで待つ。振る舞いが固まる前に適用すると、大量の機械的な変更が判定や修正と混ざる。

## 段階3: ガードレールの整備

### 目的

人と AI のどちらが変更しても、誤りが構造によって起こせないか、早く機械的に見つかる状態にする。あわせて、エージェントが自分で動作を確かめられる手段を用意する。

前提として、どの貢献者も「開いたファイルしか見ず、近くの例をまね、コンパイルが通る最短の道を取る」と想定する。1つのファイルから見て正しそうな変更が、全体としても正しくなるように設計する（K: correct）。強い制約と型は、ルールファイルの調整よりも効果が大きい（S1）。

### 入力

- 段階2までのテストと記録、直したバグの事例、形式検証の候補
- 既存のコードの書き方の実態
- 使っているツールの公式文書（仕様は要確認）

### 手順

1. **現状の書き方を調べる**: 規約は理想から作らず、すでに多数派になっている書き方と、段階2で直した書き方をもとにする。
2. **設計で誤りをなくす**: 文章や検査を足す前に、誤りそのものをなくせないかを検討する（K: correct）。挙動に関わる変更は、段階2の手順と人の判断に従う。
   - 状態ごとに持ち主を1つにし、作業ごとに正しいやり方を1つにする。
   - 内部を隠し、誤った参照が失敗するようにする。
   - 手で同期している一覧を、1つの正本に置き換える。
   - エージェントがまねしそうな古いやり方と、使われていないコードを消す。使われていないことは、確かめてから消す。
   - 検証、型の絞り込み、エラーの扱いは、システムの境界（引数、設定、外部 API、ネットワーク）に集める。内側では型を信頼し、業務ロジックは純粋な関数に置く（K: principle-boundary-discipline）。
3. **機械的な検査を、順に入れる**: 一度に全部を厳しくしない。
   1. フォーマッタ（挙動を変えない整形）。整形だけの変更として単独で入れる。
   2. linter。誤りを見つけるルールから入れる。好みに関わるルールは後にする。独自の検査を足す場合は、エラーメッセージに「代わりに使うファイル、型、関数」を書く（K: correct、G2）。
   3. 型。境界（外部との入出力、モジュールの公開部分）から入れ、厳しさを段階的に上げる。
   4. テストの拡充。リスクの高い経路、過去の不具合の再発防止、境界の値を足す。
4. **既存の違反の扱いを決める**: 違反が多い場合は、次の方式を検討する（各ツールがこの方式に対応しているかは要確認）。
   - 新しい違反だけを止め、既存の違反は記録して段階的に減らす。すでに広まっている書き方は、変更がそれを増やしたときだけ失敗させる（K: correct）。
   - 既存の違反を黙って無効化しない。例外は該当の行に置き、理由、期限、人の承認を付ける（K: correct）。
5. **検証スキルを作る**: 利用者と同じ操作でアプリを動かし、証拠を残す手順を、プロジェクト内のスキルとして用意する（G1、K: create-verification-skill）。生成用のスキル（出典では `/create-verification-skill`）が使える環境ならそれを使う。使えるかどうかと、スキルの置き場所は要確認。使えない場合も、次の要件を満たすものを作る。
   - まずリポジトリを調べる。利用者が触る面（画面、CLI、API など）、起動の方法、操作の手段（既存の仕組みを優先する）、取れる証拠、複数を並べて起動できるか。コードから分からないことだけを人に聞く。
   - 次の節を、プレースホルダーを残さず、このプロジェクトの実際のコマンドで書く。

     | 節 | 内容 |
     |---|---|
     | 起動 | 検証用に起動する正確なコマンドと、使える状態になったことの見分け方。空のデータから、移行と初期データを含めて使える状態に達すること |
     | 診断 | 「この起動中のものを操作してよいか」を答える、読み取りだけの検査 |
     | 操作 | 実際のセレクタやコマンドを使った操作の手順。座標ではなく、安定した手がかりを使う |
     | 証拠 | 何を記録し、どこに置くか。実際の利用者の経路を通ること、操作とその結果の状態の両方を記録すること、副作用（書かれたファイル、追加された行、送られたメッセージ）も確かめること |
     | 後片付け | 自分が起動したものだけを止める。証拠は消さない |
     | 補助スクリプト | 実行できる状態で置き、呼び出し方を本文に書く |

   - 機能の一覧を付ける。機能ごとに、何であるか、どうたどり着くか、どう操作するか、何が観察できれば動いていると言えるかを書く。前提が足りず確かめられない場合は失敗として報告し、手順を弱めて通さない。
   - 渡す前に、手順を最初から最後まで一度実行する。起動、診断、機能を1つ操作、証拠の記録、後片付けの順に行い、後片付けのあとに証拠が残っていることを確かめる。一度も実行していないスキルは下書きである。
   - 検証スキルはバージョン管理し、人もエージェントも同じ方法でアプリを動かす（G1）。
   - 開発環境の準備も繰り返せるようにする。初期データ、テスト用の利用者、環境を同じ形で立ち上げる1つのコマンドを用意する（G1）。
6. **危険度の高い箇所を形式検証する**: 段階2で挙げた候補から対象を選ぶ（G1、K: create-formal-verification-skill）。生成用のスキル（出典では `/create-formal-verification-skill`）が使えるかは要確認。
   - 対象は「コードが守ると約束している性質で、破れると利用者に害があり、テストが届きにくいもの」とする。検証しやすいものではなく、最も重要なものを選ぶ。
   - 道具は、問いに合わせて選ぶ。出来事が悪い順序で起こりうるかは、設計の小さなモデルに対するモデル検査が合う（出典は TLA+ を既定としている）。あらゆる入力で正しく動くかは、コードの上で動く検証器が合う。対象の言語で動く検証器がなければそう明記し、生成した入力で実際のコードをテストする。対象の言語とツールの対応は要確認。
   - 1つの性質を検証し、その性質が、壊した版のコード（検査を外す、手順を入れ替えるなど）で失敗することを示す。失敗するところを見たことがない検査は、何も証明していない。
   - 現在のコードが性質を破っていたら、反例をコードの言葉で報告する。性質やモデルを弱めて通さない。製品のコードは、頼まれない限り変えない。
   - 範囲を正直に書く。何を、どの上限と前提で検証し、何を対象外としたか。合格が保証するのはモデルや上限の範囲であり、システム全体ではない。
   - 1つのコマンドで再実行できるようにし、対象のファイルや関数と、検証がコードと一致していることを最後に確かめたコミットを記録する。対象のコードが変わったら、検証を見直す（出典では `/maintain-formal-verification-skill`）。
7. **自然言語の規約を書く**: 機械で検査できず、判断が要るものだけを書く。守られなくても何も失敗しないので、最小限にする（S5、K: correct）。
   - 命名規約: 用語集の確定した用語と、コード上の識別子の対応。使ってはいけない別名。
   - コーディング規約: 層の分け方、エラーの扱い、テストの書き方、挙動を変える変更とリファクタリングを分けること。
   - 各項目に理由を書く。
   - 機械で検査できる規約は、文章にせず linter や型やテストに移す。構造で直せたものは、文章の指示を残さない（K: principle-encode-lessons-in-structure）。
8. **AI エージェント向けのルールファイルを置く**: ファイルの名前、置き場所、読み込まれ方は、使うツールによって違うので確かめる（要確認）。内容は次のとおり。
   - ビルド、テスト、lint、型チェックの実行方法
   - 検証スキルと形式検証の場所と、使う場面
   - 用語集、ADR、判定の台帳の場所と、仮説と確定の区別
   - 人の判断が必須の作業（このスキルの線引きを、プロジェクトに合わせて具体化したもの）
   - 触ってはいけない場所、未判定の印が付いたテストの扱い
   - 変更の単位と、報告に含めること（何を確かめ、何を確かめていないか、証拠の場所）
   - ルールと強制手段の対応表（下記）

   短く保ち、詳しい内容は参照先に置く。人向けの規約と内容が食い違わないよう、正本を1つにする。
9. **ルールと強制手段の対応表を作る**: ルールごとに、それを強制しているもの（設計、型、lint、テスト、なし）を対にして書く（K: correct、G2）。強制手段が「なし」のルールは、段階5で構造に移す候補である。

   ```markdown
   | ルール | 強制しているもの | 根拠となる事例 | 追加した日 |
   |---|---|---|---|
   | （例: データの取得は所定の層を通す） | （例: lint の検査名） | （事例へのリンク） | |
   | （例: 命名は用語集に従う） | なし（判断が要る） | | |
   ```

10. **検証の仕組みを作る**:
    - 変更のたびに、テスト、lint、型チェックが自動で走り、通らない変更は取り込めないようにする。
    - 手元と CI で、同じコマンドを実行する（K: correct）。
11. **ガードレール自体を検証する**: 新しい検査ごとに、実際の過去の誤りで失敗することを確かめる（K: correct）。段階2で直したバグの事例を使う。事例がない検査は、わざと誤りを入れた変更を試しに作り、止まることを確かめる。確かめたら、その変更は捨てる。

### 人のレビューの代わりに保証するもの

| 保証したいこと | 手段 | 証拠 |
|---|---|---|
| 既知の誤りが再び入らない | 設計、型、lint、テストによる強制 | 過去の誤りで検査が失敗した記録 |
| 変更が実際に動く | 検証スキルで、利用者と同じ経路を動かす | 画面や端末の記録、応答、副作用の確認 |
| 害の大きい性質が破れない | 形式検証 | 壊した版で失敗した記録、範囲と上限の記述 |
| 規約が守られている | 機械で検査できるものは検査に移す。残りは対応表で「強制なし」と明示する | 対応表 |

人の判断が残る箇所: 何を守る性質とするかの決定、例外と緩和の承認、挙動に関わる設計変更の取り込み。理由は「人の判断が残る箇所と理由」のとおり。

### 成果物

- フォーマッタ、linter、型の設定
- 拡充したテスト
- 検証スキルと機能の一覧
- 形式検証（対象を選んだ場合）と、その範囲の記述
- 命名規約とコーディング規約
- AI エージェント向けのルールファイルと、ルールと強制手段の対応表
- 自動検証の設定
- 既存の違反の一覧と、減らす計画

### 完了条件

- 検証が自動で走り、通らない変更を取り込めない。手元と CI で同じコマンドが動く。
- 規約とルールファイルが、正本として1か所にある。
- 既存の違反と例外が把握され、例外に理由、期限、承認が付いている。
- 各検査が、実際に誤りを止めることを確かめてある。
- 検証スキルが、最初から最後まで一度は実行され、証拠が残っている。
- 形式検証の候補のそれぞれについて、実施したか、見送った理由が書かれている。

### 次の段階に進む判定

小さな実作業を、AI エージェントにルールファイルと検証スキルだけを頼りに試させる。次の3点が確認できたら、段階4に進む。

- 誤りがガードレールで止まる。
- エージェントが、検証スキルで動作を確かめ、証拠を出せる。
- エージェントが、人の判断が必須の作業で止まる。

## 段階4: 完了条件の確認と運用

### 目的

「安全に AI 駆動開発を回せる」と言える状態を確認し、その状態を保つ運用を決める。検証は、人を待つために最も遅くなりやすい工程である。エージェントが検証できるようにして、人が詰まりにならないようにする（G1）。

### 入力

- 段階1〜3の成果物
- 試行した AI 作業の記録

### 手順

1. **完了条件を確認する**: 次のチェックリストを、プロジェクトに合わせて具体化する。満たしていない項目は、理由と対応の時期を書く。目標値を置く場合は仮置きとし、実測後に見直す。
   - [ ] ビルド、テスト、実行が、文書の手順だけで再現できる
   - [ ] リスクの高い経路がテストで守られ、テストが安定している
   - [ ] 検証が自動で走り、通らない変更は取り込めない
   - [ ] 検証スキルがあり、利用者と同じ操作で動作を確かめて証拠を残せる
   - [ ] 危険度の高い箇所について、形式検証を実施したか、見送った理由が書かれている
   - [ ] 用語集と ADR があり、仮説と確定が区別されている
   - [ ] 判定の台帳があり、未判定の箇所が一覧になっている
   - [ ] AI エージェント向けのルールファイルがあり、人の判断が必須の作業が明記されている
   - [ ] ルールと強制手段の対応表があり、強制手段のないルールが把握されている
   - [ ] エージェントの権限が必要な範囲に絞られている（本番、秘密情報、取り消せない操作）
   - [ ] リリースを戻す手順があり、試してある
   - [ ] 判断を担う人（仕様、挙動を変える変更の取り込み、リリース、ガードレールの変更）が決まっている
   - [ ] 試行した AI 作業で、誤りが取り込み前に検査で見つかっている
2. **AI 作業の流れを決める**:
   1. 依頼。目的、範囲に加えて、完了の条件を「実行できる検査」として書く（G1）。例: 「既存の出力は1バイトも変わらない」「新しい出力が構文として読める」「どちらも見本のデータで実行する」。
   2. エージェントが計画を出す。検証できる単位への分け方を含める。
   3. 小さな単位で実装する。単位ごとに検査を通してから進む。
   4. 自動検証を通す。
   5. 変更の種類に合った方法で、実物を確かめる（G1）。

      | 変更の種類 | 確かめ方 |
      |---|---|
      | CLI | 実際のコマンドを実行する |
      | 画面 | 起動したアプリで、変えた流れを操作する |
      | パーサーや移行 | 保存しておいた入力を再生する |
      | 性能 | 前後の計測を比べる |
      | 保存 | 書いた値を読み戻す |

   6. 書いたエージェントとは別のエージェントが、実物を動かして独立に検証する（G1）。
   7. 人の判断が必須の種類の変更は、判断の材料と証拠を付けて人に回す。
   8. 取り込む。

   エージェントの報告には、実行したコマンドと出力、証拠の場所、確かめていないことを書かせる。長い作業や無人の作業では、決定の記録（原則12）を残させる。
3. **任せる範囲を段階的に広げる**:
   - リスクの低い作業（テストの追加、守られた範囲のリファクタリング、文書）から始める。
   - 変更の種類ごとに、「保証の手段があり、実際に誤りを止めた実績がある」ことを確かめてから、人のレビューを外す。
   - 広げる判断は人がする。
4. **記録を残す**: AI の失敗、人が行った訂正と指摘、CI の失敗、戻した変更を、あとで分類できる形でためる。これが段階5の入力になる。人が同じ訂正を繰り返したら、必ず記録する。
5. **検証の手段を保つ**: アプリが変わると、機能の一覧は古くなる。
   - 検証スキルを定期的に点検する（出典では `/maintain-verification-skill`。使えるかは要確認）。機能ごとにコードを読み、すべての機能を実際に動かす。結果は「問題なし」「検証スキルを直した」「進められなかった（理由）」のどれかで報告する（K: maintain-verification-skill）。
   - 点検で直すのは、検証スキル自身だけである。製品の退行が見つかったら、文書を直して隠さず、退行として報告する。
   - 頻度は、出典の手引きでは少なくとも1日1回としている（G1）。このプロジェクトでの頻度は要確認。
   - 形式検証は、対象のコードが変わったら見直す。
6. **知識を保つ**:
   - 新しい決定は ADR に、新しい用語は用語集に書く。
   - 仕様の疑問は、段階1の質問票の方式で聞く。
   - 定期的に、仮説のまま残っているものと保留リストを見直す。
7. **引き継ぎと終了時の扱い**: 契約に従い、成果物の引き渡しと、手元に残した資料の削除を手順に入れる。

### 人のレビューの代わりに保証するもの

| 保証したいこと | 手段 | 証拠 |
|---|---|---|
| 作業が依頼を満たしている | 完了の条件を、実行できる検査として先に書く | 検査ごとのコマンドと出力 |
| 変更が実際に動く | 検証スキルで実物を動かす | 画面や端末の記録、副作用の確認 |
| 書き手の思い込みが通らない | 別のエージェントが、実物を動かして検証する | 独立した検証の記録 |
| 長い作業の経過を追える | 決定の記録を、証拠へのポインタつきで残す | 記録と、抜き取りで確かめた結果 |

人の判断が残る箇所: 任せる範囲の拡大、挙動を変える変更の取り込み、本番へのリリース。理由は「人の判断が残る箇所と理由」のとおり。

### 成果物

- 具体化した完了条件と、その確認の結果
- AI 作業の流れの文書
- 失敗と訂正の記録の置き場所
- 検証スキルの点検の結果

### 完了条件

- チェックリストの各項目が、満たされているか、例外として承認されている。
- 実際の作業が、決めた流れで複数回まわっている（回数の目安は要確認）。

### 次の段階に進む判定

- 失敗や訂正の記録の中に、同じ種類の誤りが繰り返し現れている。
- 段階0で見つけた「繰り返されている誤り」があれば、それを最初の対象にできる。
- 繰り返しのない事例だけのうちは、段階5を始めない。1回きりの事例からルールを作ると、過剰なルール化になる。

## 段階5: 繰り返す誤りを構造に落とす改善ループ

### 目的

同じ誤りを、人の訂正やレビューで毎回拾うのをやめる。誤りの種類ごとに、リポジトリの側を変えて、次のエージェントがその誤りを起こせないようにする（G2、S4、K: correct）。

- エージェントが、収集、分類、対策の作成、証明までを担う。
- 人は、緩める変更と、ループ自体の設定を承認する。
- 反映したあと、効果を測る。

誰かが変更の流れを見続け、同じ補助関数の3つ目や、広がっていく lint の無効化といった兆候に気づく役割が要る。抜いた雑草は、二度と生えないようにルールに変える（S3）。この役割の定期的な実行を、エージェントに持たせる。

### 入力

- 人がエージェントに行った訂正（同じ訂正の繰り返しを含む）
- AI の失敗の記録（誤った変更、やり直し、止まるべき所で止まらなかった事例、不要に止まった事例）
- 最近のコミット、取り消された変更、レビューの指摘、回避策を説明するコメント（K: correct）
- CI の結果（失敗の内訳、実行時間、結果が揺れるテスト）
- lint の無効化や例外の増え方、似たコードの重複
- 取り込み後に見つかった不具合
- 現在のルールと強制手段の対応表、テスト、lint の設定、規約

### 手順

1. **集める**:
   - 入力を決まった形で記録する。項目は、何が起きたか、どこで見つかったか（手元、CI、検証スキル、人の指摘、取り込み後）、関係する変更、関係するルール。
   - 記録に、秘密情報や個人情報を入れない。
2. **誤りを種類にまとめる**: 事例を、原因が同じものどうしでまとめる。
   - 出典のスキルは、2回起きたものを1つの種類として数える（K: correct）。このプロジェクトでの閾値は仮置きとし、要確認。
   - 1回きりの事例は、影響が大きいものを除いて対象にしない。
   - 原因が次のどれかに当たる場合は、扱いを分ける。

     | 原因 | 扱い |
     |---|---|
     | 仕様の知識の不足（用語集や ADR にない、見つけにくい） | ルールを足さず、用語集や ADR を足す。段階1の質問票に回す |
     | 既存のルールが曖昧、または矛盾している | 新しく足さず、書き直す |
     | ガードレールの誤検知、過剰な制約（正しい変更が止められた） | 緩める変更として、人の承認に回す |
     | 検証の仕組みの問題（遅い、結果が揺れる） | 仕組みを直す |

3. **最も高い段で直す**: 種類ごとに、効く範囲で最も強い手段を選ぶ（K: correct、G2）。
   1. **設計でなくす**: 持ち主を1つにする、正しいやり方を1つにする、内部を隠す、手で同期する一覧をなくす、まねされる古いやり方を消す。
   2. **型で書けなくする**: 誤った状態を表せないようにする。それでも書けるなら、lint や CI の検査を足す。エラーメッセージには、代わりに使うべきものを書く。すでに広まっている書き方は、増やしたときだけ失敗させる。
   3. **テストで捕まえる**: 振る舞いを表明する。振る舞いが壊れても通るテストや、内部を変えただけで落ちるテストは、直すか消す（テストの削除は人の承認を取る）。
   4. **文書やルールに書く**: 判断が要るものだけにする。構造にできない教訓は、指示を目立たせ、失敗の例を添える（K: principle-encode-lessons-in-structure）。

   構造で直せた場合は、構造だけで直し、文章の指示は足さない（K: principle-encode-lessons-in-structure）。報告には、選んだ段と、それより高い段が使えなかった理由を書く（K: correct）。
4. **1種類を1つの変更で直す**: 頻度の高い種類から直す。効果を切り分けられるよう、関係のない対策を1つの変更にまとめない。
5. **証明する**: 対策ごとに、次を確かめて証拠を残す。
   - 新しい検査が、実際の過去の誤りで失敗する（K: correct）。
   - 正しく通るべき変更の例が、止められない。
   - 手元と CI で、同じコマンドが動く。
   - 検証の時間への影響。
6. **対応表を更新する**: ルールと強制手段の対応表（段階3）を直す（K: correct）。
   - 新しい対策を、ルールと強制手段の対として足す。
   - 表にすでにあるルールで、強制手段がないものが再発したら、同じ変更の中で最も高い段に上げる。
   - 誤りが起こせなくなったルールは、表と文書から消す。
7. **承認と反映**: 下の「自動で変えてよい範囲」の表に従う。承認者は役割名で決めておく。
8. **効果を測る**:
   - 反映の前後で指標を比べる。
   - 効果がない、または副作用が大きい変更は、取り下げるか直す。
   - 測った結果を、変更の記録に書き足す。
9. **周期を決める**: ループを回す頻度は、記録のたまり方に合わせて決める（要確認）。人がエージェントを訂正したときは、周期を待たずに、訂正の記録と対応表の確認を行う。事例が少ない期間は回さない。

### 人のレビューの代わりに保証するもの

| 保証したいこと | 手段 | 証拠 |
|---|---|---|
| 対策が本当に誤りを止める | 実際の過去の誤りで、検査が失敗することを確かめる | 失敗の記録 |
| 対策が正しい変更を妨げない | 正しく通るべき変更の例をためておき、前後で通ることを確かめる | 評価用の事例の結果 |
| 強制されていないルールが放置されない | ルールと強制手段の対応表 | 「強制なし」の一覧と、その推移 |
| ループがガードレールを弱めない | 緩める変更を、機械的に見分けて人の承認に回す（見分け方は要確認） | 承認の記録 |

人の判断が残る箇所: 緩める変更と例外の承認、ループ自体の設定、自動の範囲を広げる判断。理由は「人の判断が残る箇所と理由」のとおり。

### 自動で変えてよい範囲と、人の承認が必要な範囲

下の表は初期の案である。プロジェクトで合意して文書にし、その文書の変更も人の承認を必須にする。

| 区分 | 内容 |
|---|---|
| エージェントが自動でしてよい | 記録の収集と分類、指標の集計と報告、対策の作成と証明、強制手段のないルールや重複したルールの洗い出し、過去の失敗事例を使った対策の事前検証 |
| 事前に合意があれば、自動で反映してよい | 挙動と強制力を変えない修正（文書の誤字、リンク切れ、用語集と規約の表記の同期など）。範囲は明文化し、反映の記録を残す |
| 最初は人の承認を必須とし、実績を見て「事前の合意」に移してよい | ガードレールを強める変更（検査やテストの追加、型を厳しくする変更）のうち、証明（過去の誤りで失敗する、正しい変更の例が通る、検証の時間への影響）が揃い、書き手とは別のエージェントが実行して確かめたもの。移す判断は人がする |
| 人の承認が必須 | 自然言語のルールや規約の追加と変更、必須の検証の構成の変更、AI エージェント向けのルールファイルの内容の変更、挙動に関わる設計の変更 |
| 人の承認が必須で、特に慎重に扱う | ガードレールを緩める変更すべて（ルールの削除や無効化、例外の追加、型の厳しさを下げる、テストの削除・スキップ・期待値の変更、必須の検証を外す、形式検証の性質やモデルを弱める）、エージェントの権限の変更、このループ自体の設定（自動で変えてよい範囲、承認者、指標、閾値）の変更 |

- ループを動かすエージェントは、自分の対策を自分で合格と判定しない。
- 緩める方向の変更は、事例がいくつあっても自動にしない。
- 誤りが起こせなくなったルールの削除（手順6）は、強制手段が実際に働くことの証明を付けて、人の承認に回す。

### 暴走と過剰なルール化を防ぐ仕組み

- **1回の失敗で対策を作らない**: 再発したもの、または影響が大きいものだけを対象にする（閾値は要確認）。1回きりの変わった事例は逸話であり、ルールではない（G2）。
- **根拠のないルールを置かない**: すべてのルールに、根拠となる事例、追加した日、強制しているものを付ける。
- **文章を増やさない**: 文章のルールは最後の手段にする。ルールファイルと規約の分量に上限を決める（値は要確認）。上限に達したら、足す前に、構造への移行、統合、削除を検討する。
- **1回の周期で出す変更の数に上限を置く**（値は要確認）。
- **定期的に棚卸しする**: 発火していない、効果が測れない、他と重複または矛盾しているルールや検査を、削除の候補として人に示す。
- **変更は小さく、1つずつ**: 1種類を1つの変更にする。
- **事前に検証する**: 過去の失敗事例と、正しく通るべき変更の例を、評価用の事例としてためておく。
- **止める条件を決めておく**: 次のどれかが起きたら、ループを止めて人が見直す。
  - 指標が悪化した。
  - 誤検知が増えた。
  - 検証の時間が大きく伸びた。
  - 承認者の負担が増えた。
- **すぐ戻せるようにする**: すべての変更はバージョン管理し、単独で戻せるようにする。
- **指標を目的にしない**: 指標を良く見せるための変更（テストを弱める、失敗を記録しない）を禁止する。こうした変更は、緩める変更として扱う。
- **読むだけのレビューを重ねない**: 対策の確認に、動かさずに読むだけのエージェントのレビューを何度も通さない。目的を知らない確認役は重要でない点を拾いやすく、書き手はそれを考えずに受け入れやすい（S6 のスレッド内の返信）。確認は、実行の結果で行う。
- **人の注意を守る**: 承認の依頼が形だけにならないよう、案の数を絞り、根拠と証拠と影響を短く示す。
- **ルールやスキルを、別の作業の途中で直さない**: 不具合に気づいても、それ自身の変更として分ける。機能の作業に混ざると、確認も評価もできない（G2）。

### ループの指標

目標値は仮置きにし、実測後に見直す。

| 見たいこと | 指標の例 |
|---|---|
| 誤りが再発していないか | 同じ種類の誤りの再発数、人が同じ訂正を繰り返した回数、取り込み後に見つかった不具合の数、戻した変更の数 |
| 早く見つかっているか | 誤りが見つかった場所の内訳（手元、CI、検証スキル、人の指摘、取り込み後） |
| 構造に落ちているか | 対策の段ごとの内訳（設計、型と lint、テスト、文章）、強制手段のないルールの数 |
| 人の負担 | 人の指摘の数と種類、人の判断を待った時間、依頼から取り込みまでの時間 |
| ガードレールの質 | 誤検知の数、無効化や例外の数と期限切れの数、結果が揺れるテストの数、検証の実行時間 |
| ルールの健全さ | 文章のルールの数と分量、発火していないルールの数、追加と削除の比 |
| ループ自体 | 対策の採用の割合、提出から反映までの時間、反映後に取り下げた変更の数、承認者の所要時間 |

### 成果物

- 失敗と訂正の記録と、種類の一覧
- 自動で変えてよい範囲の合意文書
- 対策の変更と、その証明、承認の記録
- 更新したルールと強制手段の対応表
- 評価用の事例
- 指標の定期的な報告
- 棚卸しの結果

### 完了条件

- ループが、収集から効果の測定まで一巡以上まわっている。
- 反映した対策のそれぞれに、過去の誤りで検査が失敗した証拠がある。
- 対応表が最新で、強制手段のないルールが一覧になっている。
- 自動の範囲と承認の範囲が、文書になっている。
- 止める条件と、戻す手順がある。
- 指標が定期的に報告されている。
- ルールの追加だけでなく、構造への移行、統合、削除も実際に行われている。

### その後の判定

- 自動で反映してよい範囲と、人のレビューを外す変更の種類を広げるかどうかは、指標と実績をもとに人が決める。
- 指標が悪化したら、範囲を狭める。

## よくある失敗と回避策

| 失敗 | 回避策 |
|---|---|
| 一括で書き直そうとする | 段階的に置き換える。旧経路を消す条件を先に決める |
| テストを置く前に直し始める | 修正の前に特性テストを置く。テストできない構造なら、差し込むための最小限の変更を先に、単独で入れる |
| 現状の振る舞いを、確認なしにバグと決めて直す | 判定は決定者に求める。「仕様ではないが依存されている」を見落とさない |
| 特性テストが、誤った振る舞いを仕様として固定したまま残る | 未判定の印を付け、判定の台帳で追う |
| リファクタリングと挙動の変更を混ぜる | 変更を分ける。リファクタリングは、テストの結果が変わらないことで確かめる |
| AI の仮説が、確定として広まる | 状態を必ず分ける。根拠と「分からない」の選択肢を必須にする。確定は決定者の確認による |
| 回答者が流れで「はい」を選ぶ | 根拠を示す。重要な決定は ADR で決定者の確認を取る |
| 質問が増えすぎて、答えてもらえない | 聞く前に掘る。動かせば分かることは動かす。答えで実装が変わらない質問は捨てる。問数に上限を置き、止まる質問を優先する |
| 答えがチャットや通話に散らばり、同じことを聞き直す | 正本に書き戻した時点で確定とする。聞く前に、用語集と ADR を調べる |
| きれいにしやすい箇所から始める | リスクと変更の頻度で優先度を決める |
| linter や型を一度に厳しくして、大量の変更と無効化が生まれる | 段階的に入れる。新しい違反から止める。例外には、理由、期限、人の承認を付ける |
| テストを通すために、期待値やチェックを書き換える | 緩める変更は、人の承認を必須にする。期待値の変更を判定の台帳と結びつける |
| カバレッジの数字を追い、意味の薄いテストが増える | リスクの高い経路と、過去の不具合を優先する。振る舞いを壊すと落ちるかで、テストの価値を確かめる |
| 同じ誤りを、人がレビューのたびに指摘し続ける | 指摘を記録し、段階5で設計、型、lint、テストに落とす。人のレビューを強制の手段にしない |
| 人のレビューを、保証の手段が整う前に外す | 変更の種類ごとに、検査が実際に誤りを止めた実績を確かめてから外す |
| 「コンパイルが通った」「テストが通った」だけで完了とする | 実物を動かして確かめ、コマンドと出力や記録を証拠として示す |
| エージェントに、動かさずに読むだけのレビューを何度もさせる | 確認は、実行の結果か決定的な検査で行う。書き手とは別のエージェントが動かして検証する |
| 一度も失敗するところを見ていない検査を信用する | 検査ごとに、過去の誤りや壊した版で失敗することを確かめる |
| 検査を通すために、検証する性質やモデル、検証の手順を弱める | 性質は書いたとおりに保つ。破れていたら、発見として報告する。弱める変更は緩める変更として扱う |
| 形式検証の合格を、システム全体の保証として扱う | 範囲、上限、前提、対象外を明記する。対象のコードが変わったら見直す |
| 検証スキルや機能の一覧が古くなり、誤った手順で確かめる | 定期的に点検し、すべての機能を実際に動かす。製品の退行は、文書を直して隠さない |
| ルールファイルが長くなり、守られなくなる | 機械で検査できるものは、設計、型、lint、テストに移す。対応表で強制手段を管理し、分量に上限を置く |
| 失敗のたびにルールを足す | 再発と影響で絞る。最も高い段で直し、構造で直せたら文章は足さない。効果を測る |
| 改善ループが、自分でガードレールを緩める | 緩める変更と、ループ自体の設定の変更は、必ず人が承認する |
| 承認が形だけになる | 人に回すのを判断の要る点に絞る。根拠と証拠と影響を短く示す。承認者の負担を指標に入れる |
| 確かめていないことを、確かめたように報告する | 確かめたことと確かめていないことを、分けて報告する。未確認は「要確認」と書く |
| 契約や機密の確認をせずに、外部の AI サービスへ送る | 着手前に確認する。了承がなければ、許可された範囲に縮小する |
| 知識を持つ人が離れてから聞こうとする | 診断で連絡の取れる期限を確かめ、期限が近ければヒアリングを最優先にする |

## エージェントの振る舞いのまとめ

1. 最初に、着手前の確認と段階0の現状診断を行い、方針書の初版を出す。
2. 作業のたびに、いまどの段階の、どの領域の、どの手順かを方針書に照らして示す。
3. 作業は、検証できる小さな単位に分ける。単位ごとに検査を通してから、次に進む。
4. 完了の報告には、実物を確かめた証拠（実行したコマンドと出力、記録の場所）を付ける。確かめていないことは、そのとおりに書く。
5. 各段階の完了条件と、次に進む判定を満たしたかを、根拠とともに報告する。満たしていない項目は、そのとおりに書く。
6. 人の判断が必須の作業に当たったら、止まる。そのうえで、判断の材料、証拠、推奨を短く示す。
7. 同じ訂正を2度受けたら、指示を覚え直すのではなく、リポジトリの側を変える対策を、最も高い段で提案する。
8. 自分が書いた変更を、自分で合格と判定しない。検査を通すために、テスト、期待値、検証する性質を弱めない。
9. 新しく分かったこと、決まったこと、未決のことを、用語集、ADR、判定の台帳、対応表、方針書に書き戻す。
10. 数値やツールの仕様は、確かめてから書く。確かめていないものは「要確認」とする。
