# 回答の集め方

English: [Answer collection](../answer-collection.md)

段階1では、エージェントが質問票を送り、回答を正本に書き戻します。このページは、質問票の送り方と回答の受け取り方を扱います。内容は、エージェントが提案する方法、提案のときに伝える懸念、そのうちの1つ（GitHub をデータベース、Slack を入力、Claude アーティファクトを表示に使う方法）の構築の手引きです。

手順そのものは、[`skills/legacy-to-add/SKILL.md`](../../skills/legacy-to-add/SKILL.md) の「回答を集める方法の提案」にあります。正本はスキル本文で、このページはその補足です。

Claude アーティファクトについての記述は、2026-11-19 に取得した Claude ヘルプセンターの2つの記事によります（[出典](#出典)）。Slack、GitHub、Claude の画面の細部は、このページでは確かめていません。それらは「要確認」と書いてあります。適用する前に、現在の公式文書で確かめてください。

## 変わらないこと

どの方法を選んでも、次はスキル本文のとおりです。

- **2つの条件**: 正本が1か所である。変更の履歴が残る。
- **段階1の質問票の規則**:
  - 1問では1つのことだけを聞く。
  - 送る前に絞る。送るのは、答えがないと作業が止まる質問と、優先度の高い質問だけにする。
  - 回答者に見せるのは、短い要旨、短い質問、1行の仮説、少数の選択肢と「分からない」だけにする。
  - どの質問も、おおよそ10秒以内に答えられる。
  - 根拠と分類は、エージェント側の台帳に残すか、折りたたむ。
- **書き戻し**: 入力口で受けた回答は、正本に書き戻し、回答者か決定者がその変更を確認した時点で確定とする。

## エージェントが提案し、ユーザーが選ぶ

エージェントは、質問票を初めて送る前に、下の方法を推奨つきで提案して待ちます。ユーザーが選ぶまで、送信も構築もしません。選ばれた方法と正本の場所は、方針書に書きます。

| 方法 | 入力 | 正本 | 表示 | 回答者に要るもの | 向く場合 |
|---|---|---|---|---|---|
| A. リポジトリ内の文書だけ | 質問票の文書を送り、回答をエージェントかユーザーが書き戻す | リポジトリ | リポジトリの文書 | 質問票を受け取る手段 | 回答者が少ない。仕組みを作る時間がない |
| B. GitHub の Issue フォーム | Issue（フォームの機能と書き方は要確認） | リポジトリ（Issue の回答を書き戻す） | GitHub | GitHub のアカウント | 回答者がすでに GitHub を使っている |
| C. 静的サイト | 別に決める（A や B など） | リポジトリ | リポジトリから生成したサイト | 入力の方法による | 用語集を読みやすく見せたい |
| D. GitHub + Slack + Claude アーティファクト | Slack | GitHub のリポジトリ | Claude アーティファクト | Slack のアカウントだけ | 回答者が Slack を日常的に使い、GitHub や Claude のアカウントを持たない |

プロジェクトの環境に合う方法がほかにあれば、2つの条件を満たす範囲で加えて構いません。

## 方法 D: GitHub、Slack、Claude アーティファクト

```text
エージェント ──質問を投稿──▶ Slack ──ボタンか返信──▶ 書き戻しの経路 ──コミット──▶ GitHub（正本）
                                                                                    │
回答者 ◀──────────── 閲覧だけ ◀──────────── Claude アーティファクト ◀── ここから生成 ─┘
```

- **GitHub が正本**: 用語集（1用語1ファイル）、ADR、質問票、回答の記録を、履歴の残るリポジトリに置きます。対象プロジェクトのリポジトリでも、文書用のリポジトリでも構いません。場所は方針書に書きます。
- **Slack が入力**: エージェントが、チャンネルか DM に質問を投稿します。1メッセージに1問とし、選択肢と「分からない」をボタンにします。回答は、Slack アプリ（Block Kit のインタラクティブ機能）かワークフローを通じて、GitHub に書き込む経路に渡します。経路は、小さな bot、`repository_dispatch` で起動する GitHub Actions、エージェントによる返信の読み取りから選びます。
- **Claude アーティファクトは表示だけ**: 用語集と、質問ごとの状況（未回答、回答済み、反映済み）を見せます。リポジトリの内容から生成し、正本が変わるたびに作り直します。
- **回答者は、GitHub のアカウントも Claude のアカウントも要りません**。条件は、表示する内容をアーティファクトの本体に入れ、「Anyone with the link」で共有することです。先に、下の懸念2と4を確かめます。

## 方法 D を提案するときに伝える懸念

エージェントは、次のすべてを、方法 D を提案する時点で伝えます。選ばれたあとではありません。

### Claude ヘルプセンターの記載（2026-11-19 取得）

1. **アーティファクトを入力にもデータベースにもしない**: アーティファクトの共有ストレージに保存されたデータは、作成者の組織の外の人が、Claude にサインインすれば読めますが、変更はできません。Pro、Max、Ultra のプランでは、「組織の外」は作成者以外の全員を指します（[Share artifacts](#出典)）。回答者が書き込めないので、入力は Slack、データベースは GitHub にします。
2. **表示する内容は、ストレージではなくアーティファクトの本体に入れる**: サインインしていない人には、保存されたデータが見えません（[Share artifacts](#出典)）。内容が本体にあれば、「Anyone with the link」で共有したアーティファクトを、回答者は Claude のアカウントなしで見られます。この方法で共有したアーティファクトの多くはサインインなしで開けますが、内容の一部または全部を、サインイン後にだけ表示するものもあります。そのため、構築の手順7で、実物で確かめます。同じ記事から、関連する点が3つあります。
   - コネクタは人ごとです。共有されたアーティファクトでも、それぞれが自分のアプリを接続します（[What are artifacts](#出典)）。表示をコネクタに頼らないでください。
   - Docs は、サインインした人しか見られません。Claude のアカウントを持たない回答者には向きません。
   - Team と Enterprise のプランでは、オーナーが External sharing を無効にすると、「Anyone with the link」のリンクは、有効に戻すまで使えなくなります。オーナーがそのアーティファクトを個別に許可している場合は除きます。
3. **アーティファクトのストレージに、失って困るものを置かない**: レガシーのアーティファクト（2026-09-16 より前にチャットで作ったもの）を公開している場合、公開をやめる（Unpublish）と、保存されたデータが完全に削除され、そのアーティファクトをもう一度公開することはできません。あとで共有するには、新しいアーティファクトを作ります（[What are artifacts](#出典)、[Share artifacts](#出典)）。これはレガシーのアーティファクトの規則で、現行のアーティファクトすべての規則ではありません。現行のアーティファクトは「Share」で共有し、共有の停止は別に説明されています。その説明には、保存されたデータが削除されることも、再び共有できないことも書かれていません。新しく作る場合は、現行のアーティファクトを前提にします。公開済みのレガシーのアーティファクトを使い続けている人には、この規則を伝えてください。
4. **リンクを知る人は誰でも開ける**: 「Anyone with the link」で共有したアーティファクトは、リンクを知る人なら誰でも開けます。組織の外の人も、多くの場合はサインインしていない人も開けます（[Share artifacts](#出典)）。用語や回答を表示に載せる前に、顧客の機密に当たる語句を、その範囲に見せてよいかを確認します。見せてはいけない場合、「Anyone with the link」のアーティファクトは使いません。閲覧権限を設定できる表示（閲覧権限を設定した Notion のページ、非公開の静的サイトなど）を使います。

### このスキルの設計上の要件

5. **表示は正本の写しである**: アーティファクトは、GitHub の正本から生成します。正本を更新するたびに作り直すか共有し直し、生成元のコミットか日付をアーティファクトに表示します。これはこの構成の決まりで、ヘルプセンターの記載ではありません。

### 契約、プロジェクト、Slack に関する確認事項

これらも、ヘルプセンターの記載ではありません。

6. **顧客のデータが、ユーザーの Claude と Slack に入る**: 提案と構築の前に、契約と、スキルの「着手前の確認」の1（外部の AI サービスへの送信）を確かめます。了承がなければ、この方法は使いません。
7. **顧客のワークスペースへの Slack アプリの導入には、管理者の承認が要ることがある**: そのワークスペースで確認します。承認されない場合は、Workflow Builder を使うか、エージェントがスレッドの返信を読む方式に切り替えます。

## 方法 D の構築の手引き

方法 D が選ばれたら、エージェントは下の手順を1つずつ進めます。

進め方の規則:

- 手順ごとに、エージェントが作るもの（ファイル、設定の下書き）と、ユーザーが画面で行う操作（アプリの作成、トークンの発行、共有の設定）を分けて示します。ユーザーの操作が済んだことを確かめてから、次に進みます。
- Slack、GitHub、Claude の細部を、記憶で書きません。権限スコープの名前、API、設定の項目名、プランごとの条件は、先に現在の公式文書で確かめます。確かめていないものは「要確認」と書きます。
- 動かしていないコードや設定を、動作を確認したものとして渡しません。
- トークンは、チャットに貼らず、リポジトリにも書きません。

### 手順1: 前提を確かめる

- 懸念4、6、7の確認の結果を、方針書に書きます。
- 機密の語句を、リンクを知る人すべてに見せてはいけない場合は、何かを作る前に、別の表示の手段を選びます。
- Slack アプリが承認されない見込みなら、手順4の代替の方式を予定します。

**確認**: 方針書に、選んだ方法、正本の場所、それぞれの確認の結果が書かれている。

### 手順2: 正本の場所を作る

リポジトリに構成を作ります。対象プロジェクトの中のディレクトリでも、文書用のリポジトリでも構いません。[置き場所の例](usage.md#対象プロジェクトでの置き場所の例) を広げた構成の例です。

```text
docs/ai-ready/
  glossary/              # 1用語1ファイル
  adr/
  questionnaires/        # 1質問票1ファイル
  answers/               # 回答の記録。追記だけ
```

パス名は例です。スキルはパス名を定めていません。

**確認**: 場所が方針書に書かれ、ディレクトリがコミットされている。

### 手順3: 回答の形式を決める

回答の記録は、追記だけにします。1件の回答に、次を記録します。

- 質問票と質問の識別子
- 選ばれた選択肢（「分からない」と、詳しい人の名前を含む）
- 回答者（役割名）
- 回答の日時
- Slack のメッセージへのポインタ
- 状態（未反映／反映済み）

1つの質問票の記録の例です（形式はプロジェクトで決めます）。

```markdown
| 質問 | 回答 | 回答者（役割名） | 回答の日時 | Slack のメッセージ | 状態 |
|---|---|---|---|---|---|
| Q1 | はい | （役割名） | （日時） | （リンク） | 反映済み |
| Q2 | 分からない（詳しい人: ＿＿） | （役割名） | （日時） | （リンク） | 未反映 |
```

Slack のボタンの値は、質問の識別子と選択肢に一対一で対応させます。回答を、解釈を挟まずに記録するためです。

**確認**: 形式が回答の記録のそばに文書化されている。手で書いた見本の1件が、プロジェクトで使う形式の検査を通る。

### 手順4: Slack の入力を作る

次のどれかを選びます。

- **Slack アプリ**: アプリがボタンつきのメッセージを投稿し、ボタンの操作を送信先の URL で受け取ります。権限スコープは、必要な最小限にします。スコープの名前、設定の手順、送信先の側で必要な処理は、Slack の公式文書で要確認です。
- **Workflow Builder**: アプリを導入できない場合の代替です。ここでできることと、プランごとの条件は要確認です。
- **アプリなし**: エージェントかユーザーが質問を投稿し、回答者がスレッドに選択肢の番号を返信します。エージェントが返信を読みます。エージェントが Slack を読む手段は環境によるので、要確認です。

投稿先と、誰の名前で投稿するかは、ユーザーの承認を取ります。

回答者に見える1問の例です。

```text
Q1  （現状を確認する短い質問）
仮説: （1行）
[ はい ]  [ いいえ ]  [ 分からない ]
```

「いいえ」や「その他」を選んだ人は、スレッドに一言を書きます。「分からない」を選んだ人は、詳しい人の名前を書きます。

**確認**: ボタンつきの試験のメッセージが、合意した場所に表示される。アプリがどう承認されたかを、ユーザーが確認している。

### 手順5: 書き戻しの経路を作る

手順4の入力を、小さな bot、`repository_dispatch` で起動する GitHub Actions、エージェントによる返信の読み取りとコミットのどれかで、GitHub につなぎます。イベントの形式と、要る権限は、GitHub と Slack の公式文書で要確認です。

- トークンは、シークレットの保管場所に置きます。権限は、対象のリポジトリ1つへの書き込みに絞ります。
- 経路が行うのは、回答の記録への追記までです。用語集と ADR の変更は、スキルの書き戻しの手順のとおり、変更として出し、回答者か決定者の確認をもって確定とします。
- ボタンを押した人を、回答の記録に残します。宛先の役割と食い違う場合は、確定としては扱わず、ユーザーに知らせます（役割と Slack アカウントの対応の取り方は要確認）。

**確認**: ボタンを1回押すと、回答の記録にちょうど1件が、コミットとして追記される。

### 手順6: アーティファクトを作る

リポジトリから、用語集と質問ごとの状況を表示するアーティファクトを生成します。アーティファクトの作り方と共有の操作は、使う Claude の画面によるので、そこで要確認です。

- 内容は、アーティファクトの本体に入れます。ストレージ、コネクタ、入力欄は使いません。
- 仮説と確定を、見て分かるように区別します。スキルが、どの表示にも求めていることです。
- 生成元のコミットか日付を表示します。
- 共有の範囲は、懸念4の確認の結果に従います。

**確認**: アーティファクトに生成元のコミットが表示され、内容がそのコミットのリポジトリと一致する。

### 手順7: 1問で、最初から最後まで試す

試験用の質問を1つ投稿し、次を順に確かめます。

1. ボタンを押すと、回答の記録に1件が追記され、コミットが残る。
2. アーティファクトを作り直すと、その回答が状況に現れ、表示された生成元のコミットが一致する。
3. Claude にサインインしていないブラウザでリンクが開き、内容が見える。
4. 回答者が、GitHub と Claude のアカウントなしで、回答と閲覧を済ませられる。

証拠（Slack のメッセージ、コミット、画面の記録）を残します。試験の回答には、試験と分かる印を付けます。すべてが通るまで、実際の質問票は送りません。

### 手順8: 運用に入る

質問票ごとに、次を行います。

1. 要旨を1メッセージで投稿し、続けて質問を1メッセージに1問ずつ、1票ぶんをまとめて投稿する。
2. 回答が届いたら、回答の記録に追記する。
3. 用語集と ADR に書き戻し、変更の確認を取る。
4. アーティファクトを作り直し、表示された生成元のコミットを確かめる。更新したアーティファクトのリンクが変わらないかは要確認。変わる場合は、新しいリンクを送る。

Slack に届いた回答を、書き戻さないまま残さないでください。
