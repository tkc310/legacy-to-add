# 使い方

English: [Usage](../usage.md)

このページは、エージェントにこのスキルを実行させる人向けの案内です。先にスキルをインストールしてください（[インストール](installation.md)）。手順そのものは [`skills/legacy-to-ai-ready/SKILL.md`](../../skills/legacy-to-ai-ready/SKILL.md) に書いてあります。

## 使う場面

仕様や経緯が、人の記憶からも資料からも失われたプロジェクトが対象です。そのプロジェクトで、変更の安全性を「人が差分を読むこと」ではなく、構造、検査、成果物で担保して、AI 駆動開発を進めたいときに使います。

次のような状況に向いています。

- 当初の開発者がいない、または近くいなくなる。
- 資料とコードが一致しない、または資料がない。
- テストがない、通らない、または重要な経路を守っていない。
- エージェントにコードを変更させたいが、繰り返す誤りを自動で止める手段がまだない。

システムを一度に書き直す用途には使わないでください。このスキルは一括の書き直しをせず、段階的な置き換えを求めます。

## 着手前の確認

スキルは、エージェントがコードや資料を外部の AI サービスへ送る前、および変更を始める前に、次の3点の確認を求めます。

1. **契約と機密**: コードや資料を外部の AI サービスへ送ってよいか。了承がなければ、許可された範囲（たとえば端末内の処理だけ）に縮小します。
2. **書き込みの範囲**: エージェントがどのブランチ、どの環境まで触ってよいか。本番環境と本番データには、明示の許可なく触りません。
3. **判断を担う人**: 仕様を決める人、挙動を変える変更の取り込みを判断する人、リリースを承認する人、ガードレールの変更を承認する人を、役割名で確認します。担う人がいない役割は、方針書のリスクに書きます。

## プロンプトの例

Claude Code や Cursor では、`/legacy-to-ai-ready` でスキルを呼び出してから依頼を書くか、プロンプトの中でスキル名を指定します。

段階0から始める例:

> 文脈が失われたレガシープロジェクトを、安全に AI 駆動開発できる状態まで進めたいです。`legacy-to-ai-ready` スキルに従って、段階0の現状診断と方針書の初版から始めてください。方針書が承認されるまで、振る舞いは変えないでください。

途中の段階から再開する例:

> このリポジトリで `legacy-to-ai-ready` を続けてください。方針書は `docs/ai-ready/policy.md` で承認済みです。いまは課金領域の段階2です。修正の前に、現状の振る舞いを特性テストで固定してください。

人が決めることを、エージェントに決めさせない例:

> `legacy-to-ai-ready` に従って、認証領域の仕様を復元してください（段階1）。コードと履歴から、選択式の質問票を作ってください。仮説は、確定として扱わないでください。

英語の例は [Usage](../usage.md) にあります。

## エージェントに求める動き

スキルは、エージェントに次のことを求めています。

1. 最初に、上の3点の確認と段階0の現状診断を行い、方針書の初版を出す。
2. 作業のたびに、いまどの段階の、どの領域の、どの手順かを、方針書に照らして示す。
3. 作業を、検証できる小さな単位に分ける。単位ごとに検査を通してから、次に進む。
4. 完了の報告に、実物を確かめた証拠（実行したコマンドと出力、記録の場所）を付ける。確かめていないことは、そのとおりに書く。
5. 各段階の完了条件と、次に進む判定を満たしたかを、根拠とともに報告する。満たしていない項目は、満たしていないと書く。
6. 人の判断が必須の作業に当たったら止まる。そのうえで、判断の材料、証拠、推奨を短く示す。
7. 同じ訂正を2度受けたら、指示を覚え直すのではなく、リポジトリの側を変える対策を、最も高い段（設計、型や lint、テストの順）で提案する。
8. 自分が書いた変更を、自分で合格と判定しない。検査を通すために、テスト、期待値、検証する性質を弱めない。
9. 新しく分かったこと、決まったこと、未決のことを、用語集、ADR、判定の台帳、ルールと強制手段の対応表、方針書に書き戻す。
10. 数値やツールの仕様は、確かめてから書く。確かめていないものは「要確認」と書く。

スキル本文の「よくある失敗と回避策」には、起こりやすい失敗と、それぞれの回避策の一覧があります。

## 段階と方針書

作業は段階0〜5で進みます。現状診断、仕様の復元、振る舞いの固定と修正、ガードレールの整備、完了条件の確認と運用、改善ループの順です。1つの表にした概要は [README](../../README.ja.md#段階) に、段階ごとの作業、完了条件、次の段階に進む判定は [段階](stages.md) にあります。

エージェントは、段階0で方針書の初版を作り、段階が進むたびに更新します。テンプレートは2つあります。

- [`templates/policy-document.md`](../../templates/policy-document.md): 日本語。スキル本文と一致します。
- [`templates/policy-document.en.md`](../../templates/policy-document.en.md): 英語訳。

2つが食い違う場合は、日本語のテンプレートとスキル本文を正本とします。

## 人に残る判断

このスキルは、人の判断をなくそうとはしません。やめるのは、「人が差分を読むこと」を安全性の保証にすることです。

人に残る判断は、次のとおりです。

- 仮説の確定、「仕様どおりかバグか」の判定、あるべき仕様（To-Be）の決定
- 方針書と優先順位の承認
- 挙動を変える変更の取り込み（利用者や既存データへの影響を含む）
- テストや検査を緩める変更と、例外の承認
- 取り消せない操作（本番へのリリース、データの削除や移行、外部への送信）の承認
- エージェントの権限と、任せる範囲の変更

これらの判断を求めるとき、エージェントは、差分の全行を読むよう頼むのではなく、判断の材料と証拠を短く示します。

## 対象プロジェクトでの置き場所の例

スキルはパス名を定めていません。バージョン管理された場所を1か所選び、方針書に書いてください。たとえば、次の構成にすると探しやすくなります。

```text
docs/ai-ready/
  policy.md              # 方針書。段階が進むたびに更新する
  diagnosis.md           # 段階0の記録
  glossary.md
  adr/
  questionnaires/
  judgment-ledger.md
  rules-to-enforcement.md
  failures/
```

プロジェクトに、正本として使える場所がすでにあるなら、そこを使ってください。チャットでのやり取りは正本になりません。チャットで決まったことは、正本に書き戻した時点で確定とします。
