# 使い方

先にスキルをインストールしてください。手順は [インストール](installation.md) にあります。進め方そのものは [`skills/legacy-to-ai-ready/SKILL.md`](../../skills/legacy-to-ai-ready/SKILL.md) に書いてあります。このページは、エージェントにそのスキルを実行してもらう人向けの案内です。

English guide: [Usage](../usage.md).

## 使う場面

仕様や経緯が、人の記憶や資料から失われているプロジェクトを対象にします。変更の安全性を「人が差分を読むこと」で担保するのではなく、構造、検査、成果物で担保して、AI 駆動開発を回せる状態まで進めるときに使います。

次のような兆候があるときに向いています。

- 当初の執筆者がいない、または近くいなくなる。
- 資料とコードが一致しない、または資料がない。
- テストがない、通らない、または重要な経路を守っていない。
- エージェントにコードを変えさせたいが、繰り返す誤りを自動で止める手段がまだない。

システムを一度に書き直す手段としては使わないでください。このスキルは一括の書き直しをせず、段階的な置き換えを求めます。

## コードを外部の AI サービスへ送る前に

スキルは、エージェントがコードや資料を外部の AI サービスへ送ったり、変更を始めたりする前に、次の3点を確認するよう求めています。

1. **契約と機密。** コードや資料を外部の AI サービスへ送ってよいか。了承がなければ、許可された範囲（たとえば端末内の処理だけ）に縮小します。
2. **書き込みの範囲。** エージェントがどのブランチや環境まで触ってよいか。本番環境と本番データには、明示の許可なく触りません。
3. **判断を担う人。** 仕様を決める人、挙動を変える変更の取り込みを判断する人、リリースを承認する人、ガードレールの変更を承認する人を、役割名で確認します。いない役割は、方針書のリスクに書きます。

## プロンプトの例

Claude Code や Cursor では `/legacy-to-ai-ready` でスキルを呼び出してから依頼を書くか、プロンプトの中でスキル名を指定します。

段階0から始める例:

> 文脈が失われたレガシープロジェクトを、安全に AI 駆動開発できる状態まで進めたいです。`legacy-to-ai-ready` スキルに従って、段階0の現状診断と方針書の初版から始めてください。方針書が承認されるまで、振る舞いは変えないでください。

途中の段階から再開する例:

> このリポジトリで `legacy-to-ai-ready` を続けてください。方針書は `docs/ai-ready/policy.md` で承認済みです。いまは課金領域の段階2です。修正の前に、現状の振る舞いを特性テストで固定してください。

人の判断で止める例:

> `legacy-to-ai-ready` に従って、認証領域の仕様を復元してください（段階1）。コードと履歴から、選択式の質問票を作ってください。仮説は、確定として扱わないでください。

英語の例は [Usage](../usage.md) にあります。

## エージェントに求める動き

スキルがエージェントに求めているのは、次のことです。

1. 最初に、着手前の確認と段階0の現状診断を行い、方針書の初版を出す。
2. 作業のたびに、いまどの段階の、どの領域の、どの手順かを、方針書に照らして示す。
3. 作業を、検証できる小さな単位に分ける。単位ごとに検査を通してから、次に進む。
4. 完了の報告に、実物を確かめた証拠（実行したコマンドと出力、記録の場所）を付ける。確かめていないことは、そのとおりに書く。
5. 各段階の完了条件と、次に進む判定を満たしたかを、根拠とともに報告する。満たしていない項目は、満たしていないと書く。
6. 人の判断が必須の作業に当たったら止まる。そのうえで、判断の材料、証拠、推奨を短く示す。
7. 同じ訂正を2度受けたら、指示を覚え直すのではなく、リポジトリの側を変える対策を、最も高い段で提案する。
8. 自分が書いた変更を、自分で合格と判定しない。検査を通すために、テスト、期待値、検証する性質を弱めない。
9. 新しく分かったこと、決まったこと、未決のことを、用語集、ADR、判定の台帳、対応表、方針書に書き戻す。
10. 数値やツールの仕様は、確かめてから書く。確かめていないものは「要確認」とする。

失敗しやすいパターンと回避策の一覧は、スキル本文の「よくある失敗と回避策」にあります。

## 段階と成果物

作業は段階0から段階5まで進みます。段階は厳密な直列ではありません。規模が大きい場合は、領域ごとに段階1〜2を回し、対象の領域に行き渡ってから段階3に進みます。

| 段階 | 目的 | 主な成果物 |
|---|---|---|
| 0. 現状診断 | どこに力を使うかを決め、方針書の初版を書く | 診断の記録（コマンドと出力を含む）、方針書の初版 |
| 1. 仕様の復元 | 用語と決定を正本に残す | 体制の一覧、用語集、ADR、質問票と回答、保留リスト、未決事項 |
| 2. 振る舞いの固定と修正 | 現状を固定し、「仕様どおりかバグか」を判定して直す | 特性テストと仕様のテスト、判定の台帳、修正、あとの検査の証明に使うバグの事例 |
| 3. ガードレールの整備 | 設計・型・lint・テストに落とし、検証スキルを置く | フォーマッタ、linter、型の設定、テスト、検証スキル、形式検証（行う場合）、エージェント向けルール、ルールと強制手段の対応表、CI |
| 4. 完了条件の確認と運用 | 安全に回せることを確認し、運用の流れを決める | 具体化した完了条件、AI 作業の流れ、失敗と訂正の記録場所 |
| 5. 改善ループ | 繰り返す誤りを構造に落とし、ガードレールとハーネスを調整する | 失敗の種類の一覧、自動で変えてよい範囲の合意、検査の証明、指標 |

完了条件と、次の段階に進む判定の詳細は [段階](stages.md) を見てください。

エージェントは、段階が進むたびに方針書を更新します。ひな型は [`templates/policy-document.md`](../../templates/policy-document.md)（日本語。スキル本文と一致）と、[`templates/policy-document.en.md`](../../templates/policy-document.en.md)（英語訳）です。食い違う場合は、日本語のひな型とスキル本文を正本としてください。

## 人に残る判断

このスキルは、人の判断をなくそうとはしません。なくそうとしているのは、「人が差分を読むこと」を安全性の保証にすることです。

人に残る判断は、次のとおりです。

- 仮説の確定、「仕様どおりかバグか」の判定、あるべき仕様（To-Be）の決定
- 方針書と優先順位の承認
- 挙動を変える変更の取り込み（利用者や既存データへの影響を含む）
- テストや検査を緩める変更と、例外の承認
- 取り消せない操作（本番へのリリース、データの削除や移行、外部への送信）の承認
- エージェントの権限と、任せる範囲の変更

エージェントは、差分の全行を読んでほしいと頼むのではなく、判断の材料と証拠を短く渡すべきです。

## 対象プロジェクトでの置き場所の例

スキルはパス名を定めていません。バージョン管理された1か所を選び、方針書に書いてください。探しやすい例は次のとおりです。

```text
docs/ai-ready/
  policy.md              # 方針書。段階が進むたびに更新する
  diagnosis.md           # 段階0の記録
  glossary.md
  adr/
  questionnaires/
  judgment-ledger.md
  rules-to-enforcement.md
  failures/
```

すでに使っている場所が正本になれるなら、それを使ってください。チャットに二通目を残さないでください。
